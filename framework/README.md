# desktop

The desktop framework: desktop apps with a Go backend and a Vue +
TypeScript frontend, on [Wails v3](https://v3.wails.io/). A project holds
only the app. The framework owns everything else: the main package, Wails,
the generated bindings, and the Vite and TypeScript configuration.

The goal is a surface small enough that an agent, including one on a
non-frontier model, has few ways to get it wrong.

It is this monorepo's framework, run by the harness through
`framework.yaml`: `harness test`, `record`, `run`, `build`, and `cli` in a
project's folder, or with `-p <project>`, run its verbs. It changes with its
projects: a breaking change here and the changes it needs in each project
land in the same pull request. `harness test` in this folder runs the
framework's own Go tests, then every project's.

The framework's command runs from this folder, with `go run`, so a project
is always built with the library beside it, at the same commit. Each
project's `go.mod` says so with a `replace` of the framework's module by
`../../framework`, so a project also builds with Go alone.

It needs Go 1.26+ and Node.js 20+. It needs no C compiler, Xcode, or GTK
headers: apps are built without cgo, using Wails' purego backend, which
loads the system's UI libraries when the app starts. On Linux, running an app
needs GTK 4 and WebKitGTK 6.0 installed (Debian 12, Ubuntu 24.04, and later).

The framework keeps what every project shares in `~/.harness/desktop/`: its
tools, the browsers for tests and recordings, and downloaded dependencies.
All of it can be downloaded again, so deleting it is always safe.

## A desktop project

```
desktop.yaml      name, modes, window, data folder, dependencies
desktop.lock      written by desktop when there are dependencies; commit it
go.mod, go.sum    the project's one Go module
package.json      the project's one npm package, and its package-lock.json
backend/          a Go package: your services
frontend/         Vue + TypeScript
database/         optional: SQL that builds the database, in order
  <mode>/         optional: a mode's own migrations, such as fixtures
tests/            optional: e2e tests, in Go
  <mode>/         the tests of one mode, against the app built in it
cli/              optional: a command-line program; see `harness cli`
.desktop/         generated by desktop; ignored by git on its own
build/            written by `harness build`; also ignored by git
```

The project is one Go module and one npm package, both at the root, so
`go get`, `go test ./...`, and `npm install` work where you type them, and
there is no second module to keep in step. `backend/`, `tests/`, and `cli/`
are packages of the module; code they share can go in `internal/`.
`go.mod` needs one line besides the usual: `ignore ./node_modules`. Go does
not skip `node_modules` on its own, and some npm packages ship Go files, so
`go build ./...` would try to compile them. Desktop says so if it is
missing, and also if a `backend/go.mod`, `tests/go.mod`, or
`frontend/package.json` is left from before both moved to the root.

The app is built with the desktop library that came with the `harness`
command you ran, not the version in `go.mod`: the checkout you ran
`go install ./cmd/desktop` in, or the copy Go downloaded for
`go install …@version`. So the app always matches the command, nothing is
fetched from the private repository, and desktop changes that aren't pushed
yet work at once. `go test` under `harness test` and the build in
`harness cli` do the same, through a generated `.desktop/work/go.work`. `go.mod`
still needs a `require` line for desktop, for your editor and for `go`
commands you type yourself. If your checkout moves to another commit after
you install, desktop warns you and builds with the checkout's library; run
`go install ./cmd/desktop` there to match. A project that has its own
`replace` for desktop in `go.mod` keeps it.

### `desktop.yaml`

```yaml
name: My App              # required
id: com.example.my-app    # optional; defaults to local.desktop.<name>
data: ~/.my-app           # optional; defaults to ~/. and the last part of id
icon: assets/icon.png     # optional; see The icon
default_mode: prod        # required with more than one mode
modes:                    # optional; see Modes. With none, the one mode is prod
  prod:
  dev: { name: My App Dev, id: com.example.my-app.dev, icon: assets/dev.png }
window:                   # optional
  title: My App           # defaults to name
  width: 1024
  height: 768
deps:                     # optional; see Dependencies
  jq:
    darwin/arm64: https://github.com/jqlang/jq/releases/download/jq-1.7.1/jq-macos-arm64
    linux/arm64: https://github.com/jqlang/jq/releases/download/jq-1.7.1/jq-linux-arm64
menu:                     # optional; see The menu
  settings: open-settings
  Notes:
    - New note: { key: CmdOrCtrl+N, event: new-note }
browser: true             # optional; see The browser
```

`id` is how the operating system tells apps apart: macOS keeps an app's
settings and permissions under it. Set it once and leave it. The default is
built from `name`, so renaming the app would otherwise make it a different
app.

`data` is the built app's data folder. It must be a folder inside the home
folder, written with `~/`, so it works for any user. See Data and the
database.

Unknown fields are an error.

### The icon

`icon` is the path, relative to `desktop.yaml`, of a square PNG at least
1024x1024. Desktop makes every form of it a platform needs: an `.icns` in
the macOS bundle, and the icon of the Windows `.exe`. The running app shows
it in the macOS Dock, also under `harness run`, and in the Windows taskbar.
On Linux, GTK 4 takes an app's icon only from an installed `.desktop` file,
which desktop does not write, so a Linux window has none. With no `icon`, the
app has the system's default.

### Modes

A mode is a version of the app, such as `prod` for users and `dev` with
tools for its developers. Each mode is built on its own, and has its own:

- **name, id, and icon**, from `modes.<mode>.name`, `.id`, and `.icon`,
  defaulting to the top-level ones. No two modes may share either: macOS would take two apps
  with one id for one, and two with one name would replace each other in
  `build/`. A window title left to default follows the mode's name.
- **data folder**: `<data>/data/<mode>` for the built app, and
  `.desktop/data/<mode>` under `harness run`.
- **migrations**: those in `database/`, and its own in `database/<mode>/`.
- **e2e tests**, in `tests/<mode>/`.
- **frontend**: `DESKTOP_MODE` is the mode's name, replaced as the frontend
  is built. A check of it in a script leaves another mode's code out of the
  bundle, imports and all:

  ```ts
  const DevBar = DESKTOP_MODE === "dev" ? defineAsyncComponent(() => import("./DevBar.vue")) : null;
  ```

  Its type lists the modes, so a misspelt one is a type error. A template
  cannot see it: Vue reads a template's names at runtime, so the bundle
  would keep both branches. In a unit test it is the default mode, and
  `vi.stubGlobal("DESKTOP_MODE", "dev")` changes it.

`harness modes` prints a project's modes as JSON, the default first, each
with its app's name: what Slipway's mode picker lists. `harness run` and `harness record start` run `default_mode`, or the one
`-mode=<mode>` names. `harness build` builds every mode, and `harness test`
runs each mode's e2e tests against the app built in that mode.

### `backend/`

A Go package, `<module>/backend`, that exports `Services`:

```go
package backend

import "github.com/michaelckearney/monorepo/framework"

func Services() []desktop.Service {
	return []desktop.Service{
		desktop.NewService(&Greeter{}),
	}
}
```

Every exported method of a service can be called from the frontend. The
backend imports `harness`, never Wails.

### `frontend/`

An `index.html` that loads your Vue app, and its source in `src/`. The
`package.json` at the root must list `vue`, `vite`, and
`@vitejs/plugin-vue`. Desktop tells you the command to run if one is
missing. Don't install `@wailsio/runtime`: desktop builds it from the
source in the Wails module it pins, so it always matches the Go side, and
`import { Browser } from "@wailsio/runtime"` resolves to that.

Services are imported from `@backend`:

```ts
import { Greeter } from "@backend";
const greeting = await Greeter.Greet("Ada");
```

`@/` is `frontend/src/`, as most Vue tooling expects. A
`postcss.config.mjs` in `frontend/` is used, so Tailwind works through
`@tailwindcss/postcss`.

For editor support, `frontend/tsconfig.json` is one line:

```json
{ "extends": "../.desktop/tsconfig.json" }
```

There is no `vite.config.ts`. Desktop generates it.

### `@ui`, the shared frontend

`framework/ui` is the frontend every app shares, so a change to it reaches
them all: the design system (`style.css`: the sizes, spacing, colours, and
base styles), the built-in themes and what puts one on the window
(`themes.ts`), shadcn-vue's components (`components/button`, `dialog`,
`input`, `popover`, …), and the app's own parts built from them: a
resizable, collapsible side panel, Settings over the window, Markdown, an
agent's transcript, a theme picker, an icon button, and a tooltip. Desktop
copies it into `.desktop/ui`, and the frontend imports it as `@ui`:

```ts
import { Button } from "@ui/components/button";
import SidePanel from "@ui/components/SidePanel.vue";
import { applyTheme } from "@ui/themes";
```

An app's `frontend/src/style.css` starts with the design system:

```css
@import "../../.desktop/ui/style.css";
```

The shared parts keep nothing themselves: where a panel's width or the
theme in use is kept is the app's, which passes it in and saves what they
give back. It is a copy rather than a link, so its imports of npm packages
find the project's `node_modules`; an app that uses a part lists the
packages it imports (`reka-ui`, `lucide-vue-next`, `markdown-it`, …).

## Data and the database

```go
dir := desktop.DataDir() // the app's data folder, created on first use
db := desktop.DB()       // *sql.DB for app.db in that folder
```

The data folder depends on how the app was started, so developing and testing
the app never touches a user's real data:

| Started by | Data folder |
|---|---|
| `harness run` | `.desktop/data/<mode>/`, kept between restarts; delete it to start over |
| `harness test`, `harness record` | a new, empty folder for each run |
| the built app | `data/<mode>` in `data` from `desktop.yaml` |

`desktop.DB` is SQLite, through a pure Go driver, so server builds and tests
need no cgo. It is opened with foreign keys on, write-ahead logging, a
five-second wait for a lock, and transactions that take the write lock when
they begin. Call it from `Services` or later, not when a package is
initialized:

```go
func Services() []desktop.Service {
	return []desktop.Service{
		desktop.NewService(&Notes{db: desktop.DB()}),
	}
}
```

**Migrations** are files named `<number>_<words>.sql`: `001_create_notes.sql`,
`002_add_tags.sql`. Those at the top of `database/` are every mode's; those in
`database/<mode>/` are that mode's alone, such as the fixtures a developer
build starts with. The numbers run from 1 with no gaps across all the folders
together, so each number is one file, and a mode skips the others' numbers.
They only go forward. The app applies new ones when it opens the database,
each in its own transaction; a migration that fails changes nothing and stops
the app. Desktop embeds a mode's migrations in that mode's build only, and
`harness run` restarts the app when anything in `database/` changes.

A migration is a Go template, so a document can be kept as its own file
rather than escaped into SQL. `{{file "assets/notes/welcome.md"}}` is that file
in the `assets/` folder beside the migration, as a quoted SQL string:

```sql
-- database/dev/003_fixtures.sql
INSERT INTO notes (title, body) VALUES ('Welcome', {{file "assets/notes/welcome.md"}});
```

A migration runs once, so editing an asset later changes only new databases.
Delete `.desktop/data/<mode>` to start one over.

**A second database**, such as a sandbox the app runs something in and then
deletes, is `desktop.NewDB(path)`: a new file at `path` with the migrations
every mode shares, not the mode's own. The caller closes it.
`desktop.Mode()` is the mode the app was built in, as `DESKTOP_MODE` is in
the frontend, for a backend with something only one mode has.

**Go tests** get their own database:

```go
func TestNotes(t *testing.T) {
	n := Notes{db: desktop.TestDB(t)} // new, with the migrations every mode has
	...
}
```

`desktop.DataDir` also works in Go tests run by `harness test`, where it is an
empty folder. In a plain `go test`, it panics: use `t.TempDir()`.

## Live queries

The frontend can read the database directly, and the result stays current:

```ts
import { sql, useQuery } from "@desktop";

const folder = ref("inbox");
const notes = useQuery<Note>(() =>
  sql`SELECT id, body FROM notes WHERE folder = ${folder.value} ORDER BY id`
);
```

`notes.value` is the rows. Like `computed`, the query runs again when a value
in it changes, such as `folder`. Unlike `computed`, it also runs again when the
data under it changes, whatever wrote it: a Go method the frontend called, a
goroutine in the background, or another program writing to the file. It works
the same in a component and in a Pinia store. The getter can return `null` to
have no query, and no rows.

- Each `${value}` is sent as a parameter, never pasted into the SQL. Write it
  bare, not in quotes: `WHERE name = ${name}`, and
  `LIKE ${"%" + text + "%"}`.
- Live queries run on a read-only connection. They can read anything and
  change nothing; save data through Go methods.
- Rows are objects keyed by column name. Give two columns with the same name
  different names with `AS`. A BLOB arrives as a base64 string.
- The array is read-only and replaced on every change. Rows that did not
  change keep the same objects, so Vue does not redraw them.
- A query that fails logs the error and the query to the console, and keeps
  its last rows.

Unit tests mock `@desktop`, as they mock `@backend`:

```ts
vi.mock("@desktop", () => ({
  sql: (s: TemplateStringsArray, ...args: unknown[]) => ({ text: s.join("?"), args }),
  useQuery: () => ref([{ id: 1, body: "hi" }]),
}));
```

How it works: desktop asks SQLite which tables each query reads (with
`EXPLAIN`, which sees through joins and views), and hooks on every connection
record which tables each committed write changed. Only the queries that read
a changed table run again. Each new result is compared with the last one, row
by row, and only the rows that differ are sent; a result that did not change
sends nothing. A write from another program is noticed within a quarter of a
second, and reruns every query.

## The menu

The app always has the standard menus: the app menu, File, Edit, View, and
Window. `menu` in `desktop.yaml` adds your own:

```yaml
menu:
  settings: open-settings       # adds Settings… on ⌘, to the app menu
  File:
    - New note: { key: CmdOrCtrl+N, event: new-note }
    - separator
    - Export…: export           # an item with no shortcut
  Notes:
    - Archive: { key: CmdOrCtrl+E, event: archive }
```

Menus appear in the order written. Items in `File` or `Help` go in that
standard menu; any other menu goes between View and Window. `Edit`, `View`,
and `Window` are filled by the system and cannot be added to. On Linux,
Settings… goes in File.

A shortcut is modifiers and a key joined by `+`. The modifiers are
`CmdOrCtrl`, `Shift`, `OptionOrAlt`, `Ctrl`, and `Super`. The key is one
character, or a name such as `Backspace`, `Enter`, `Up`, or `F5`.

Choosing an item sends its event to the frontend:

```ts
import { onMenu } from "@desktop";

onMenu("new-note", () => notes.create());
```

`onMenu` works in a component and in a Pinia store, and stops when that
does. Event names are checked: `harness test` fails on an event the menu
does not send. The menu is fixed: items cannot be greyed out or ticked while
the app runs.

The e2e tests and recordings run the app in a browser, which has no menu bar.
Test what a handler does with a unit test, with `onMenu` mocked:

```ts
const menu = vi.hoisted(() => new Map<string, () => void>());
vi.mock("@desktop", () => ({
  onMenu: (event: string, handler: () => void) => { menu.set(event, handler); return () => {}; },
}));
// later: menu.get("new-note")?.();
```

## Links

A link in the app leads out of it. Call `openLinksInBrowser` once, in
`main.ts`, and every link opens in your browser, never in the app's window,
whoever made it: a component, a page, or Markdown. The middle button and
`window.open` do too, and a link with `download` saves its file.

```ts
import { openLinksInBrowser } from "@desktop";

openLinksInBrowser();
```

## The browser

An app that uses websites for its user, signed in as them, sets
`browser: true` in `desktop.yaml`. Desktop then adds the Chromium it pins to
the app's dependencies, as `chromium`, and the frontend's `@desktop` gets
`useTab` and `LiveView`. The design, and why, is in `docs/browser.md`.

```go
import "github.com/michaelckearney/monorepo/framework/browser"

b := browser.Open(browser.Options{ // one headless Chromium, on browser/ in DataDir
	HTTPAuth: func(ctx context.Context, r browser.AuthRequest) *browser.Credentials { ... },
	Passkey:  func(ctx context.Context, r browser.PasskeyRequest) (json.RawMessage, error) { ... },
	Dialog:   func(ctx context.Context, tab *browser.Tab, d browser.Dialog) (bool, string) { ... },
	// ChooseFiles, Downloaded
})
defer b.Close()

tab, err := b.Open(ctx, "https://example.com/")
raw, err := tab.Evaluate(ctx, `() => document.title`)
tab.ID()       // for useTab and LiveView
tab.State()    // URL, Title, Loading, CanGoBack, CanGoForward
tab.Opened()   // the tabs it opened, such as a pop-up

snap, err := tab.Snapshot(ctx, 0) // the page as its accessibility tree: `button "Go" [ref=e12]`
err = tab.Click(ctx, "e12")       // and Type, Select, Check, Press: as your mouse and keys would
```

Headless Chromium shows nothing of its own, so each box a page asks for is a
hook: a nil hook refuses. `Expose` gives a page a function that calls Go, and
tells Go which site really called it. `browser/passkey` and
`browser/securitykey` answer a `Passkey` request in software or with a USB
key, and `browser/totp` makes an authenticator app's codes; they keep
nothing.

```ts
import { LiveView, useTab } from "@desktop";
const tab = useTab(() => id.value); // tab.url, tab.opened, tab.back(), ...
```

```vue
<LiveView :tab="id" style="height: 70vh"><MyPrompt v-if="asking" /></LiveView>
```

`LiveView` shows one tab, live, sized to fit, and sends it your mouse and
keys; its slot is drawn over the page. Frames come as Wails events, so no
call stays open: the window's WebKit lets only about six be open at once.
Headless Chromium paints one tab at a time, so show one `LiveView` at a time.

## Dependencies

Files the app needs at runtime, such as a compiler, are listed
under `deps` in `desktop.yaml`: a name, then one download URL per platform.
The platforms are `darwin/arm64`, `darwin/amd64`, `linux/arm64`,
`linux/amd64`, `windows/arm64`, and `windows/amd64`. A platform with no URL
is an error only when desktop runs or builds the app for that platform.

```go
dir := desktop.Dep("jq") // the folder the download was unpacked into
```

- A zip, tar.gz, or tgz is unpacked into the folder, as it is in the archive.
- Anything else is one file in the folder, named after the dependency, on
  every platform: `desktop.Dep("jq")` + `/jq`. A `.gz` is decompressed first.
  The file is made executable.

Desktop downloads each file once, into `~/.desktop/deps/`, and the project
sees it as `.desktop/deps/<name>`. The cache is keyed by each file's sha256,
not its URL, so worktrees on different versions run side by side, and
worktrees on the same version share one copy.

The first download of a URL writes its sha256 to `desktop.lock`. Commit it.
After that, a download that does not match is refused, so a file that changed
at the same URL does not slip in. To accept a new file on purpose, delete its
line from `desktop.lock`.

`harness build` embeds each download in the app's binary, so the built app
needs nothing beside it. The first time the app calls `desktop.Dep` for a
dependency, it unpacks it into its data folder, in `deps/<name>-<hash>/`;
later calls and later launches reuse that folder. A new version unpacks
once, and the old one is deleted. The built app never uses `~/.desktop`.

Embedding needs the file as it was downloaded, which the cache does not keep,
so the first build after a download fetches it again, checked against
`desktop.lock`, into `~/.desktop/deps/downloads/`. `harness build` builds for
every platform, so it also downloads each platform's file, and records the
sha256 of any `desktop.lock` does not have yet.

## `harness run`

Run it from anywhere inside the project. It:

1. links `node_modules` to the install for your `package.json` and
   `package-lock.json`, running `npm install` first if there is none yet
   (see [Packages](#packages))
2. generates `.desktop/` and the TypeScript bindings for your services
3. starts the Vite dev server and builds and opens the app
4. in a git repository, serves the control API the Slipway app uses (see
   [Running another branch](#running-another-branch))

While it runs:

- editing `frontend/` hot-reloads the window
- editing `backend/`, or any Go package the app could import, `go.mod`
  and `go.sum` among them, regenerates the bindings, rebuilds, and restarts
  the app; if the build fails, the running app stays open. `tests/` and
  `cli/` are not watched: the app does not import them
- editing `database/`, or `desktop.yaml`, does the same as a backend edit

Closing the app's window or pressing Ctrl-C stops everything. Every line of
output is labelled `desktop:`, `[vite]`, `[app]`, `[go]`, or `[npm]`,
so you can see which part it came from.

### Running another branch

In a git repository, `harness run` serves a control API on 127.0.0.1, and
writes where it is to `.desktop/run.json` while it runs. The Slipway app
reads that file: open the project there to list your checkout, the open pull
requests, and the other local and remote branches, and pick one to run it in
the app's window in place of what is running.

- **Pull requests** come from the `gh` command, if it is installed and signed
  in. Each one shows its number, title, author, and whether its checks
  passed. Without `gh` the list has only branches. The list is fetched when
  the run starts, every five minutes, and when you click Refresh.
- **Your checkout is never changed.** A branch is checked out at its newest
  commit into `.desktop/worktrees/<branch>/`, and runs from there. A local
  branch that its remote branch is ahead of runs at the remote commit. Do not
  edit the worktrees: desktop discards changes to them on the next switch.
- **Edits follow what is running.** desktop watches the checkout that is
  running, so editing your checkout updates the app while your checkout is
  the one running.
- **Each branch has its own data.** The first time a branch runs, it starts
  with no data, so its database has exactly the branch's migrations, and the
  mode's own, such as its fixtures, give it something to show. The data is
  kept between switches. Reset data deletes it, and the branch starts again
  with none.
- **A pull request from a fork** is marked, and runs only after you confirm.
  Running it runs its Go code and its npm install scripts on your computer.
- **If a branch does not build**, what was running keeps running, and the
  app shows the error. The details are in the terminal.

`run.json` holds the API's `url` and a `token`, readable only by you. Every
request must carry the token in an `X-Desktop-Token` header, which a web
page elsewhere cannot read or set. Its `api` field is the API's version.

```
GET  /api/state     what is running, the branches, and the run's status
POST /api/switch    {"key": "<branch key>", "trust": false}: run another branch
POST /api/reset     delete the running branch's data, so it starts again with none
POST /api/refresh   fetch, and ask GitHub for the pull requests again
POST /api/open      {"key": "<branch key>"}: open its pull request in a browser
```

The same server's root is a page with the list, for a browser when the app is
not at hand: open the `url` with `?token=<token>`.

### Packages

Each checkout's `node_modules` is a link into `.desktop/packages/` of your
own checkout. That folder has one install for each different pair of
`package.json` and `package-lock.json`. Branches with the same packages use
the same install, and a branch you have run before switches back without
npm. desktop adds `node_modules` to the repository's `.git/info/exclude`,
because a link does not match the `node_modules/` pattern in `.gitignore`.
The first run moves an existing `node_modules` into the cache. You can still
run npm in your checkout as usual: the next run sees the change and makes a
new install from the changed one. Delete `.desktop/packages/` to clear the
cache.

## `harness build`

Builds the app in every mode for every platform, from macOS or Linux, and
puts each platform's builds in a folder of their own in `build/`, each under
its mode's name:

- `build/darwin-arm64/` and `build/darwin-amd64/`: `<name>.app`
- `build/linux-arm64/` and `build/linux-amd64/`: `<name-in-lower-case>`, a
  single executable
- `build/windows-arm64/` and `build/windows-amd64/`:
  `<name-in-lower-case>.exe`, a single executable

`build/` is emptied first. A platform that fails, such as one a dependency
has no URL for, does not stop the others: desktop builds the rest, lists
what it built, and then fails, naming each platform that did not build and
why.

It is a production build: the frontend is built by Vite once per mode and
embedded in every platform's binary. The app is compiled without cgo, using
Wails' purego backend, so every platform builds from any machine, with
nothing but Go. Wails calls that backend experimental. Builds are not
signed, so macOS will warn on any Mac other than the one that built it; an
arm64 macOS build has the ad-hoc signature Go gives it, which it needs to
start at all.

The version is the harness's: it comes from git, from the project's latest
release tag and the pull requests merged since that changed its folder
(see Releasing), such as `0.5.0` on the tagged commit and
`0.5.0-dev.abc1234` anywhere else. macOS and Windows show only the numbers,
`0.5.0`. Each build is also packed as a release asset in `build/release/`:
a macOS `.app` zipped, such as `harbor-darwin-arm64.zip`, each other build
copied, and `SHA256SUMS`, which `harness release` publishes.

The built app keeps its data in `data/<mode>` in `data` from `desktop.yaml`,
and its binary carries that platform's dependencies (see Dependencies).

## `harness record`

Evidence for a change: an agent drives the app step by step, then desktop
replays the steps into a video, screenshots, and a report.

```bash
harness record start                 # builds and starts the app, lists what is on screen;
                                     # -mode=<mode> for a mode other than the default
harness record fill e6 Ada           # act with the [ref=...] names from that list
harness record click e7              # each step prints what appeared and what went away
harness record see "Hello, Ada"      # a claim: fails if the text is not on screen
harness record shot "greeting shown" # a screenshot, captioned by what it shows
harness record stop                  # replays everything into .desktop/recordings/<time>/,
                                     # and prints the path of each file it writes
```

Run `harness record` for the full list. It is a curated part of
[Playwright CLI](https://playwright.dev/docs/getting-started-cli):

- **actions**, which are recorded: click, dblclick, fill, type, press, hover,
  select, check, uncheck, drag, drop, upload, dialog-accept, dialog-dismiss,
  mousewheel
- **looking and diagnosing**, which are not recorded: snapshot, find,
  console, requests and the request details, and the cookie and storage
  list and get commands
- **desktop's own**: `see`, `not-see`, `shot`, and `restart`, which quits and
  reopens the app to show what survives

Left out on purpose: anything that can put on screen what the app never did
(`eval`, `run-code`, network mocking, storage setters), anything desktop
controls (opening, closing, video, window size, emulation, tabs), and
navigation a desktop app does not have (`goto`, back, forward).

Nothing is filmed while the agent works, so its thinking time is not in the
video. `stop` starts a fresh app and replays the steps at a steady pace, with
each action labelled on screen and each screenshot's caption shown as a title
card. If a step behaves differently on the fresh app, the replay stops there
and the report says which step.

A failed step records nothing and prints the whole screen list, so the next
attempt can use a name that is there. Elements are found by what a person
reads: text, labels, and `aria-label`s. An element with none of these cannot
be found again in the replay, and desktop warns when one is used.

Recording uses the same server build of the app as the e2e tests, so the
operating system's own menus and file dialogs are not part of it. The app
starts with a new data folder, which `restart` keeps; the replay starts with
another. Playwright CLI and its WebKit are installed into `~/.desktop/` on
first use; the project gets no new files or packages.

## `harness test`

Runs three phases in order and stops after the first one that fails:

| Phase | Go (the module) | Frontend (`frontend/`) |
|---|---|---|
| lint | `gofmt`, `go vet` | `vue-tsc` type check |
| unit | `go test`, every package but `tests/` | Vitest |
| e2e | `go test` in `tests/<mode>/`, against the app built in each mode | |

`-lint`, `-unit`, and `-e2e` run only the phases you name, still in that
order. `harness test -lint -unit` is the fast check: it needs no browser.

Every check in a phase runs before the phase stops, so all of a phase's
problems are reported at once. File names in the output are relative to the
project root.

**Go tests** sit beside the code, in `backend/`, `cli/`, or any package, as usual. They are built as a Wails server
build, with no cgo, so they run on a Linux machine without GTK or WebKit.
`desktop.Dep` works in them, and `desktop.TestDB(t)` gives a test its own
database.

**Frontend unit tests** go in `__tests__/` directories under `frontend/src`,
named `<name>.test.ts`. A test file anywhere else fails the unit phase, since
it would never run. Unit tests mock `@backend`:

```ts
vi.mock("@backend", () => ({ Greeter: { Greet: vi.fn(async () => "hi") } }));
```

The `package.json` also needs `typescript` and `vue-tsc` for lint,
and `vitest` and `jsdom` for unit tests. Add `@vue/test-utils` to mount
components.

**E2E tests** are in `tests/`, with each mode's tests in `tests/<mode>/`
and the packages under it. A test file anywhere else in `tests/` fails the
unit phase, since it would never run; shared helpers without tests may go
anywhere. They are packages of the project's module, so they can import the
backend's.

For each mode with tests, the e2e phase builds the frontend and a server
build of the app in that mode, starts it with a new data folder, so the
database has only that mode's migrations, and runs `go test` on
`tests/<mode>/...`. A mode with no tests is not built.

Package `github.com/michaelckearney/monorepo/framework/e2e` opens the app in WebKit, the
browser engine Wails uses on macOS and Linux, through
[playwright-go](https://github.com/mxschmitt/playwright-go):

```go
func TestGreeting(t *testing.T) {
	page := e2e.Open(t) // the app's first page, in a browser context for this test
	e2e.Do(t, page.GetByPlaceholder("Your name").Fill("Ada"))
	e2e.Do(t, page.GetByRole("button", playwright.PageGetByRoleOptions{Name: "Greet"}).Click())
	e2e.Expect(t, page.GetByText("Hello, Ada!")).ToBeVisible()
}
```

- `e2e.Do` fails the test if an action returned an error.
- `e2e.Expect` has the common assertions, which wait up to five seconds:
  `ToBeVisible`, `ToHaveText`, `ToContainText`, `ToHaveCount`, and more, and
  `Not()` before any of them.
- The viewport is the window size from `desktop.yaml`; colour scheme,
  locale, and time zone are pinned.
- A failed test keeps a trace and a screenshot in
  `.desktop/test-results/<test>/`.

The Playwright driver and WebKit are installed into `~/.desktop` the first
time. An e2e test can also skip the browser and test the backend's own code
against something real, such as a test web server: anything too slow or too
heavy for the unit phase.

The tests share one running app, so give what a test creates names of its
own.

## `harness cli`

```bash
harness cli [-mode=<mode>] <args>
```

Builds the program in `cli/`, a main package of the project's module, and
runs it with `<args>`. It is for the commands that developing the app
needs, run by a person or an agent: Harbor's runs its benchmarks.

The program runs as the app does under `harness run`: on the same data
folder, `.desktop/data/<mode>/`, so `desktop.DB()` is the database the
running app has, with the mode's migrations applied; `desktop.DataDir()`,
`desktop.Dep`, `desktop.NewDB`, and `desktop.Mode()` work as they do in the
app. Live queries notice what the program writes, so the running app shows
it. The program is a server build, with no cgo and no window.

`-mode` must come first; everything after it, or after `--`, is the
program's. It runs in the folder you ran desktop in, its output and exit
code are its own, and desktop's messages, such as a compile error, go to
stderr. A signal sent to desktop, such as a harness stopping the command, is
passed on to it.

## Releasing

`harness release` releases each project on its own, tagged
`<project>/v<version>`, such as `harbor/v0.2.0`: see the harness's README.
It builds the project with this framework's `harness build`, then publishes
the assets the build packed.

## Layout

```
framework.yaml       how the harness runs the framework
cmd/desktop/         the framework's command: the verbs, by the harness's contract
desktop.go, data.go  the package backends import
generated/           called by the generated main package only
internal/project/    reads desktop.yaml, go.mod, and package.json
internal/generate/   writes .desktop/ from templates/
ui/                  the frontend every app shares, which the frontend imports as @ui
internal/deps/       downloads dependencies and keeps desktop.lock
internal/migrate/    checks and renders database/, and applies a mode's migrations
internal/live/       live queries: hooks, reruns, and the rows that changed
internal/appstate/   what the command and the generated main tell package desktop
internal/unpack/     unpacks a dependency's download, for the command and a built app
e2e/                 the package e2e tests drive the app with
internal/home/       finds ~/.harness/desktop
internal/run/        the `harness run` loop, and the control API the Slipway app talks to
internal/branches/   lists branches and pull requests, and checks them out
internal/sidecar/    the control API's page, for a browser
internal/build/      `harness build`: every mode, for every platform
internal/pack/       the release assets of a build
internal/gitversion/ the version from the last tag and the pull request titles since
internal/icon/       the app's icon as an .icns and as Windows resources
internal/cli/        `harness cli`: builds cli/ and runs it
internal/pin/        the Wails version and the Chromium desktop is built against
internal/services/   the Wails services of desktop's optional packages
internal/version/    the framework's version
browser/             headless Chromium for an app with browser: true
```

The command does not link Wails. Only the generated app does, so the
framework needs no GTK or WebKit headers.
